## Explicit lifecycle and immutable meaning

The exact core fields are contract, action, locationId, expected, change, reason and profilePin. Contract is northstar.enterprise.location-lifecycle.v1. IDs are canonical lower-case UUIDs; nonempty pins contain exact id, positive int32 revision and lower-case 64-hex digest. Only create accepts expected {id:null, revision:0, digest:null}. Missing/null/undefined/extra fields, accessors/symbols/hidden fields in actual modules, unsupported markers and malformed text deny. Name/reason/address limits are 160/2,000/500 Unicode code points respectively, with bounded UTF-8 size, no control characters or surrounding ASCII spaces. Null address explicitly means undeclared, not inferred from a profile or provider.

| Action | Exact change | New immutable state |
| --- | --- | --- |
| create | name, address | New explicit same-company location UUID; inactive |
| activate | empty object | Inactive to active |
| deactivate | empty object | Active to inactive |
| rename | changed name | Same identity and state, new label revision |
| relocate | changed nonempty address | Same identity and active/inactive state; declared administrative relocation |
| correct | name, address, correctedRevision | Appended correction pointing to an exact existing revision of this same company/location |
| transfer | target containing locationId and pin | Same-company administrative succession to an exact current active target; source becomes terminal transferred |

Transferred locations reject every new action, including rename/correct/reactivation. Recovery of an already committed identical request returns its immutable receipt after current authority validation; it does not append another revision or make the source active. Transfer does not infer legal/common ownership, franchise participation or access. Cross-company transfer is unsupported. Source/target pins and reason remain in the history. Historical jobs, customers, workforce homeLocation references, financial records and their ownership do not move. Existing offices/headquarters are neither adopted nor mapped into canonical identities; names do not establish identity. Existing company/tenant authority remains organizations.id.

Preview invokes canonical_enterprise_location_v1_plan and returns the exact proposed values, source/target pins and review digest with confirmed:false. Commit accepts only the matching review marker/digest and confirmed:true, then recomputes the plan under current authority. This is an explicit existing owner/admin review and confirmation; it is not a two-person, professional or founder approval. A caller cannot add ownership, permission, legacy-mapping or foreign-company fields to change its meaning.

## Persistence, concurrency and currentness

The only new migration is [290_enterprise_location_lifecycle_v1.sql](../../migrations/290_enterprise_location_lifecycle_v1.sql). Source now contains 286 migrations through 290/no 291. All 285 inherited SQL bytes remain unchanged. The single new append-only table canonical_enterprise_location_revisions_v1 stores 26 columns, same-company/location revision chains, correction/target pins, current source profile pin, actor/session provenance, request/review digests and server time. Four exact foreign keys preserve organization and same-company revision references. Runtime has no table DML privilege. FORCE RLS, a company policy, private helper ACLs and a BEFORE UPDATE/DELETE/TRUNCATE statement trigger protect immutable history, including zero-row mutation attempts.

The server alone assigns both the per-location revision and positive organizationRevision. UNIQUE(organization_id,organization_revision) serializes the company ledger, while unique company/request and company/location/revision keys protect idempotency and CAS. The receipt digest includes this organization revision. A new append cannot quietly reuse an earlier company snapshot, including an append to a different location used as a transfer target.

The SQL authority helper matches the exact current session/actor/company/membership, active/null-revocation flags, database-clock access/refresh expiry, current fixed role, onboarding, credential hash, subscription and active Business Profile. Bindings preserve microsecond revision text. Mutation authority invokes the established canonical_travel_write_authority lock guard and SHARE-locks the active profile; a profile replaced after the request snapshot forces retry. Commit requires SERIALIZABLE, acquires a company advisory transaction fence and organization row lock, checks current authority, resolves idempotency, recomputes exact source/head/target/review, appends one row, then checks locked authority again. Invisible dependent appends collide on the server company ordinal and require a fresh transaction snapshot.

Repository writes have 10-second statement/idle bounds and 2-second lock bounds. One bounded retry follows a complete rollback for serialization/deadlock/uniqueness errors, preserving the same request key. Identical company/actor/body recovery returns the original receipt; changed body/key reuse or changed review denies. Read/preview requests use new REPEATABLE READ READ ONLY snapshots and reserve nothing. Currentness is the coherent checked/locked transaction observation, not a promise of future validity or cancellation/reversal of committed actions. A later independently committed revocation invalidates later requests; no retroactive cancellation is claimed.
