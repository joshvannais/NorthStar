# Mission 26 Part 11A — forecast settings contract

The unmounted `forecastSettingsContract` defines a bounded, immutable settings shape for future owner-reviewed forecast preferences. Its only system default is conservative: forecasting disabled, no targets or horizons selected, ranges and comparisons withheld, alerts off, and every possible action still review-required. NorthStar does not invent a business horizon, target, notification or statistical policy for a tenant.

An enabled owner-reviewed candidate must explicitly name target keys and weekly, monthly or quarterly horizon counts. It may request deterministic scenarios or calibrated intervals **when separately eligible**, prior/actual comparisons, and in-app review alerts. These are presentation preferences, not proof that a source is authorized, a target is registered, an algorithm is promoted, an interval is calibrated, an actual is final or a forecast can issue. Automatic action is not an accepted setting. The limits of 24 targets, 12 horizon entries and 100 periods are defensive input bounds, not recommended business values.

The contract carries a tenant, claimed candidate revision number, exact effective time, claimed owner actor and a prior settings digest after revision one. It sorts order-insensitive selections, calculates a stable digest and returns detached frozen data. It rejects duplicate grains, malformed or extra fields, a disabled profile retaining hidden active selections, and a first revision that claims a predecessor. A digest reference does not itself prove the predecessor exists, the revision is next in sequence or the claimed actor is the current owner.

This is a pure validation prerequisite, not a database record, current settings reader, permission grant, route, owner UI or final Part 11A acceptance. A future mounted path must resolve the current owner/administrator from the paid session, validate each selected target and horizon against its current target/algorithm/source authority, lock the current revision, enforce CSRF and idempotency, persist immutable revisions, confirm `supersedesDigest` against the actual current revision, and audit the change. Demo settings must remain isolated and fictional. Source eligibility and all calibration gates remain independent of preferences.

Focused tests cover the disabled default, deterministic order/digest, revision linkage, disabled hidden-selection rejection, duplicate and bounded horizons, automatic-action refusal and the fact that a calibrated-display preference authenticates nothing. Final acceptance still needs PostgreSQL persistence, concurrency and stale-revision tests; current role/tenant authorization; paid/demo settings UI and recovery; target-specific validation; rendered plain-language review; and an independent exact-head audit. CI, provider, private-production, physical-device and founder visual evidence remain separate.
