# Mission 26 Part 2A — immutable as-of source snapshots

Status: release candidate. The first bounded source capture reads the existing Mission 24 commercial-decision ledger and persists an immutable receipt. No forecast route, prediction, generic historical reconstruction or backtest is live.

## Temporal rule

An as-of time answers **what NorthStar had recorded by that instant**, not merely when the underlying event happened. A provider can send an older job record tomorrow; that record was not available to yesterday's forecast. A customer can book an appointment for next month today; that future appointment is available to today's forecast. A later correction must not be swapped into an earlier historical snapshot. Source readers must select the exact source revision whose NorthStar `recordedAt` is at or before the cutoff, and must separately retain any business `eventAt`. They must never backdate platform receipt time from a provider-supplied event date.

The manifest currently pins tenant, purpose, target, as-of time, capture time, source kind, source ID, revision, digest, NorthStar record time, optional business event time and active/tombstone state. It rejects future-recorded revisions, duplicate identities, malformed UTC times and arbitrary source fields. Pins are sorted and detached so later caller mutation cannot rewrite an accepted manifest. The 1,000-pin limit is a bounded safety limit, not a claim that 1,000 observations suffice for a target. A larger cohort needs deliberate page/chunk design and a proven aggregate digest, never an unbounded array.

## Trusted first-source capture

The shape contract cannot establish that a caller's source digest, revision, record time, tenant or consent is truthful. Migration `136_canonical_forecast_as_of_snapshots.sql` provides the first trusted, target-specific reader. An owner or admin with current membership, session, completed onboarding, eligible subscription and mutation CSRF calls the database entry in a serializable transaction. The database mints the cutoff, reads the visible latest decision revision for each estimate from Mission 24's append-only ledger, and writes a minimized immutable receipt in the same transaction. The runtime role has entry-function access but no direct table or helper access; owner-only reads recheck current entitlement and tenant. One idempotency key replays one frozen receipt.

`created_at` alone is not commit-time history: a transaction can insert a row before the cutoff and commit afterward. A new snapshot can safely capture only rows **visible in its own consistent transaction** at its database-minted cutoff. An old cutoff cannot be reconstructed later from `created_at` alone; require a previously saved snapshot or source-specific proof of historical visibility. Otherwise the historical forecast/backtest is unavailable.

The store records a canonical digest of the authorized manifest. It forbids direct runtime insert/update/delete and cross-tenant reads. The stored snapshot contains decision identity, revision, digest, record time and active/withdrawn state; it does not copy amount, raw transcript, customer details, wages or provider payload. The 1,000-pin and 262-KB limits fail closed. Larger cohorts need a separately reviewed bounded batching/aggregate design. Correction, revocation, retention and current-display invalidation remain Part 2D and Part 11C gates, while immutable historical receipts may remain only where source policy permits.

The fixed purpose is `forecast_pipeline` and the fixed target is `pipeline.approved_estimates`. This is a source-read proof, not a forecast or permission to rewrite Mission 24. The approved-estimate cohort is a source input, not the complete future pipeline feature. Other source kinds need their own owning-authority and purpose review; a generic caller-supplied manifest insert is not acceptable. No appointment event source is supported by this capture. Future-event availability must be separately proved when its owning source is added.

Focused disposable PostgreSQL tests prove current decision capture, digest/replay, denied member/cross-tenant/direct reads, access loss, immutability, and later decision exclusion from earlier receipts. Import and future-appointment behavior remain unavailable because this slice has no authority-specific reader for those sources. The test does not prove a production provider, historical replay from arbitrary timestamps, large-cohort performance or a forecast. Part 2B owns calendars/windows, Part 2C owns normalized feature values, Part 2D owns revocation/recovery, and Part 3 owns backtests/calibration. The Part 1B output contract must not accept a caller-invented snapshot digest as source authority.
