Status: released bounded implementation on deployed Part 4C authority through PR #407. It presents a current bounded backlog fact and a clearly isolated fictional example. It does not issue a demand forecast or complete Part 4.

## Paid workspace

The shared Command Center does not create a current-backlog snapshot during page load or ordinary workspace refresh. A paid owner or administrator must choose one of two explicit actions:

1. **Capture current backlog** sends an empty guarded request to `POST /api/v1/forecast/current-backlog/snapshots` with one browser-generated idempotency key. An unconfirmed retry reuses that same key. A completed action clears the attempt so a later deliberate capture has a new identity.
2. **Load receipt** requires the exact UUID returned by an earlier capture and reads only `GET /api/v1/forecast/current-backlog/snapshots/:snapshotId`. The browser rejects a response unless its receipt ID exactly matches the normalized requested UUID; a mismatch cannot replace the input or render values, and retry preserves the original request identity.

The server remains the tenant, paid-subscription, owner/admin, CSRF, idempotency, source-currentness and 500-member-bound authority. Forward migration 210 adds rolling-compatible guarded capture/read entries that attach only the immutable person-plan composition marker; it neither rewrites saved rows nor changes the migration 209 entry contracts used by an older application process. The server and browser use that marker to accept the exact pre-209 partial shape while requiring the current unresolved-linkage reason on newly composed receipts. The browser otherwise accepts only the migration 209 safe projection, mandatory false coverage and forecast flags, nonnegative bounded counts and coherent reviewed-person-minute state. It never receives member appointment, assignment, estimate, execution, review or source-generation identities. A cross-tenant receipt is indistinguishable from an unavailable private receipt.

The UI separates approved-unscheduled, approved-scheduled and in-progress counts from reviewed planned person-hours. The five mutually exclusive source-cohort counts must total at most 500, and known active backlog must exactly equal the three active-state counts. A descriptive receipt must contain at least one recorded member and no unresolved linkage. Reviewed planned time can be available only while active backlog exists; `no_active_backlog` is valid only when the active count is zero. Missing or noncurrent person-plan review makes planned time unavailable while preserving only the allowed current counts. A partial receipt is accepted only with unresolved linkage, unavailable planned time and the exact `unresolved_linkage_present` reason. `source_changed_after_capture` is reserved for the source-stale state, which withholds every count, planned time and digest. Server and browser enforce the same aggregate, active-count and state-specific planned-time invariants as the guarded producer. Supported record or response-size limits, access restriction, source contention, malformed response and workspace failure each have an explicit no-number state. Missing Command Center contract, account-session authority or exact demand-controller module starts paid receipt controls disabled and cannot issue a request. Workspace failure advances a client operation generation so a later completion from an in-flight capture or read cannot repaint hidden values. Explicit retry of an uncertain capture retains its exact idempotency key; switching to an exact receipt read abandons that capture identity so a later Capture starts a new request. Workspace recovery never silently captures a new receipt.
