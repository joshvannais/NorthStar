## Product boundary

The shared Command Center now presents one paid owner/admin demand-research workspace and one isolated fictional demo journey. It does not publish a production forecast. Current backlog remains a present-state fact and is never added to a future research output.

The paid workspace exposes only explicit actions already authorized by the accepted source boundaries:

- **Current backlog** captures or reads one exact Part 4C backlog-fact receipt, then reads its exact accepted migrations 207–210 snapshot. Stale facts withhold every number. Page load, workspace refresh and recovery do not capture a fact.
- **Inbound source research (Part 4A)** loads the current completed-month profile, explicitly captures and activates the prospective profile anchor, loads and records the exact historical-month profile attestation, checks or records the explicit company Retell research-permission decision, captures one chosen completed local-month source snapshot, immediately selects that exact bounded receipt for call review, loads and records those reviews, checks, certifies or revokes that exact monthly receipt, and saves or reads an exact future origin. This monthly path remains usable when the older all-history receipt exceeds its 1,000-call bound; the all-history control is labelled troubleshooting and is not a prerequisite for monthly certification. Part 4A has no evaluation authority, so the UI provides no inbound evaluation action.
- **Transition research (Part 4B)** checks the current four-target method review, records an explicit approve/reject decision, saves or reads a server-selected origin, and explicitly evaluates or reads that origin after its horizon. The four ordered targets are qualification, estimate request, booking and booking cancellation.
- **Seasonal and first-booking research (Part 4C)** reads a purpose-fixed current prerequisite projection, creates a prospective source epoch from the server-selected current profile anchor, records explicit method approve/reject decisions, saves or reads exact seasonal or pipeline origins, and explicitly evaluates or reads each selected origin after its horizon.

Migration 223 adds only the missing paid prerequisite read projection. It acquires the accepted profile, method and epoch fences in a fixed order; rechecks current paid owner/admin access after every blocking boundary; returns the current profile anchor plus exact method revision/digest and epoch state; and performs no write. It does not create consent, an epoch, a review, an origin or an evaluation. Private tables and helpers remain unavailable to the runtime role and `PUBLIC`; the mounted route is the only runtime entry.

Every permission, attestation, certification, epoch creation and method review remains a deliberate human action. The UI never auto-approves a method, fabricates consent or certification, chooses source members, supplies numeric forecasts or actuals, schedules work, dispatches people, promotes a lead or changes commercial records.

The period-certification route performs its server-derived evidence preflight in a normal `READ COMMITTED` transaction because the owning guarded reader takes source/profile `SHARE` locks. The preflight itself writes no receipt. Provider disagreement, access loss, source change or any later mutation refusal rolls back or returns before a certification insert; the immutable current certification and its revision/digest remain unchanged. This transaction declaration does not weaken the owning source fences or production provider-scan and request-rate limits.

## Response and identity rules

The browser validates a route-specific allowlist before painting a result. It binds normalized receipt IDs to the exact GET, binds every evaluation to both the selected origin and selected evaluation receipt, requires the ordered Part 4B target set, validates supported horizon chronology and rejects unknown states, extra fields, malformed nested prerequisite tokens and private forecast poison. Paid probability, forecast amount/count, output digest, member arrays and evaluation metrics are never rendered.

Writes use a browser-generated idempotency key. An uncertain transport or server failure keeps the exact endpoint, action, body and key for explicit retry. A known client, authorization or source-conflict response retires that identity; a changed input or later deliberate action gets a new key. Exact-ID reads retry the original normalized ID. No receipt ID is stored in browser persistence.

Command Center mode, tenant ID, workspace integrity revision/digest, session ID, workspace generation and expiry form the client workspace identity. A change clears private receipt IDs, prerequisite tokens and retry identities and advances the operation generation. Late completions cannot repaint after a workspace, session, tenant, mode or action-generation change. The backlog panel applies the same identity boundary. Ordinary page load and refresh perform zero forecast mutations.

## Visible states and recovery

The four research panels distinguish loading, missing prerequisite, current, saved, evaluated, stale, restricted, oversized/bounded refusal, invalid receipt, conflict, uncertain transport and workspace-unavailable states. Copy describes the next supported action in plain language: check the current permission/review/prerequisite token, capture or certify the named monthly source, create an explicit epoch, save a new origin, evaluate after the horizon, or retry the same uncertain action. It does not direct users to a nonexistent source-setup screen or expose migration, SQL or private source implementation details.

Authenticated zero remains distinct from missing or incomplete evidence in the guarded source authorities. The UI does not convert either condition into a displayed numeric forecast. A stale receipt remains immutable historical evidence; recovery creates a new explicit append-only action rather than rewriting it.

## Isolated demo

The demo uses deterministic fictional local state through the same four-panel presentation contract. The user explicitly approves or rejects the fictional transition method, then advances from ready, to fictional saved origins, to fictional post-horizon evaluations, to a fictional source-change state, and recovers with distinct new fictional origins. Origin and evaluation receipts remain indexed by exact ID for the life of the demo session, so an earlier receipt can be loaded as stale after recovery instead of disappearing. Reset, session expiry or workspace-generation change invalidates the old local state. Two independent demo cookies therefore retain independent journeys.

The demo never calls `/api/v1/forecast/*`, never reads or writes production tenant tables and never turns fictional output into paid evidence. The current-backlog example remains separately labelled fictional. Demo copy states that it is illustrative research, not a production forecast or commercial action.
