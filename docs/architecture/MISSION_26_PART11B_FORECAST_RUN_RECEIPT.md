# Mission 26 Part 11B — forecast run receipt prerequisite

The unmounted `forecastRunReceipt` freezes a bounded caller-supplied identity for one forecast run. It pins the tenant and prediction cutoff; Part 11A settings revision/digest; Part 2 source snapshot, reporting-window and feature-set digests; Part 3 algorithm definition and implementation digests; calculation and output-contract versions; and an ordered manifest of target/version/output digests. Run identity, creation time and an optional claimed superseded run remain outside the deterministic input/result identities. The returned receipt is detached, deeply frozen and digest-addressed.

The comparator requires two distinct run identities and makes three limited statements. `reproduced` means the two supplied receipts have identical pinned input and result manifests. `result_mismatch` means identical pinned inputs produced different output manifests. `input_changed` means the inputs differ, even if the output digests happen to match. A run cannot establish its own reproduction, and one run ID cannot name conflicting receipts. The comparator does not call an algorithm, reconstruct source data, prove that an implementation digest represents deployed code or establish that either run was genuinely produced before its outcome. Digest equality is evidence of receipt identity, not proof that the underlying claims are truthful.

An optional supersession link pins another run ID and digest plus a reason. The pure contract prevents self-reference but cannot prove that the referenced run exists, belongs to the same tenant, is current, or may lawfully be superseded. Supersession never edits or deletes an earlier receipt. A future mounted store must verify that relationship, preserve both runs and create a new immutable lineage event. Re-running with a newer source snapshot, settings revision, algorithm, window or feature set is `input_changed`; NorthStar must not call that an exact reproduction.

This is not the Part 11B immutable PostgreSQL run ledger, issue path or final acceptance. All source, algorithm, target and actor pins are caller-supplied. A mounted flow must consume the trusted Part 2A snapshot and current Part 11A settings; resolve server-side tenant/owner authority; prove target/algorithm eligibility; execute the calculation once; store the canonical outputs and receipt atomically; enforce idempotency and exact-current revisions; and prevent runtime update/delete. A reproducible rerun must load the preserved authorized inputs and executable version, rerun the calculation in a controlled environment, and compare the newly produced output manifest. If required retained inputs or code are unavailable, the rerun is unavailable rather than approximated.

Focused tests cover deterministic ordering, frozen output, equivalent supplied receipts, result mismatch, input change, supersession identity, duplicate/cross-tenant/malformed rejection and forged arrays. Final acceptance requires migration and permission design, immutable storage, concurrent replay, exact idempotency, source correction and retention behavior, actual controlled reruns, algorithm-build provenance, restart/restore, performance bounds, paid/demo isolation, current and historical reads, plain-language comparison UI, and independent exact-head review. No CI, provider, private-production, physical-device or founder visual evidence is implied.
