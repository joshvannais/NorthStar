# Mission 26 Part 6A: approved-price source-order reproduction

This test-only slice records a source-order boundary for future approved-price period coverage. It does not change production capture, authorize a forecast, or close Part 6A acceptance.

`tests/integration/m26-part6a-price-source-order-postgres.test.js` uses a disposable PostgreSQL fixture and actual concurrent transactions. It demonstrates that a serializable capture can exclude an approval committed before its wall-clock `asOf` value when its MVCC snapshot was established earlier. The existing fresh currentness read then reports the receipt as stale and withholds a forecast. Consequently, a timestamp by itself cannot certify that every approval before that time was captured.

The test also demonstrates that taking a table `SHARE` lock *inside* a serializable procedure after an approval writer is already in flight does not refresh the procedure's snapshot. A read-committed procedure that waits for the same writer and then reads does see the committed row. The latter is a diagnostic result, not a selected production design: a table-wide lock can delay approval writes across organizations and needs explicit bounded-lock, deadlock, throughput, authorization, and tenant-isolation review before use.

A separate tenant-scoped candidate is also insufficient as a complete-period proof. Locking one `organizations` parent row `FOR UPDATE` waits for an in-flight same-tenant decision insert and blocks later same-tenant inserts through their foreign-key checks, while another tenant can continue. The later insert can nevertheless receive its `created_at` value before it waits, then commit after the fence releases. The focused test proves that its recorded time can precede the capture cutoff even though the capture could not see it. A parent-row lock and wall-clock cutoff therefore cannot certify a complete `created_at` period. This experiment does not change the released Mission 24 writer or the serializable capture path.

Acceptance of complete approved-price period coverage still requires an independently reviewed source-order fence and a missing-data gate. Historical or partially covered periods must remain unavailable for live forecasting. These tests use synthetic records only and do not establish private-production or provider coverage.

Draft migration 146 adds a source-order **candidate** without rewriting a Mission 24 decision. A private insert trigger waits on a transaction-scoped tenant advisory lock, assigns a global sequence value to a tenant-bound sidecar row, and holds the lock until the decision transaction commits. Sequence gaps after rollback are valid; order is compared, never counted as a contiguous number of decisions. The synthetic concurrency test proves that a later same-tenant decision whose Mission 24 `created_at` precedes a capture clock still receives an order above the captured high-water mark. A different tenant can write while the first tenant's fence is held. Runtime cannot read or mutate the sidecar or sequence directly.

This candidate is **not yet a guarded source capture**. The released immutable v1 receipt still uses a wall-clock cutoff and SERIALIZABLE snapshot, so it remains unsuitable as complete-period proof. Future work must persist an authorized, bounded, immutable receipt that pins the source-order high-water mark, all included decision identities and a post-installation coverage start under a fresh READ COMMITTED snapshot after acquiring the same tenant lock. It must prove replay, corrections, rollback gaps, overflow, currentness, historical unsequenced rows and tenant/role denial. Until that path is implemented, independently audited and released, Part 6A and Part 12A remain open and no numerical approved-price forecast may rely on this sidecar.
