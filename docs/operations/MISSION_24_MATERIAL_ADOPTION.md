## Current implementation contract

The owner/admin customer drawer can preview and explicitly include its current saved material plan. The original estimate is implicit revision 1; [059](../../migrations/059_canonical_estimate_revisions.sql) appends immutable child rows, preserving the original graph, operation, estimate, snapshot, appointment and all earlier migrations. A tenant/root/plan uniqueness constraint prevents including the same plan twice. Parent and plan foreign keys remain tenant/root matched. Plan inputs, entered source/date, original pins, parent pins, global decision basis, actor, confirmation, request and input digests establish provenance. Later source edits or withdrawal never rewrite a saved child.

[The shared calculation](../../src/estimating/materialAdoptionContract.js) supports the known original v2 calculator and USD/CAD/EUR. It replaces the material component with the exact waste-inclusive plan total and sums applicable original labor/equipment/travel costs once. It retains exact decimal strings, supported zero, missingness, component applicability and overflow rejection. Original material 500, labor 100, equipment 50 becomes direct cost 507.50 with material 357.50; material zero gives 150.00. Missing applicable labor keeps the aggregate unavailable. Original pricing applicability must be known. Original price, tax and total remain explicitly historical references; overhead/profit/margins are not presented as recalculated. Capella compares only a newly reviewed price with the selected revision's direct costs.

[Selected review projection](../../src/estimating/estimateRevisionReview.js) preserves the exact original pin shape for R1 and adds a separate child revision namespace for successors. The selected revision's human decision/history is filtered by full pins. `decisions.writeBasis` is the latest GLOBAL decision sequence, not an inherited approval. R2 can therefore have no current decision while the next human decision correctly advances the existing global chain. Both paid/demo material writes use that global basis; the displayed plan basis separately checks selected source and human decision. R2 cannot withdraw R1 approval. A new plan against R2 can create R3, requiring another human price review.

The paid preview/read uses the same current-owner/admin read transaction. Adoption uses SERIALIZABLE and the existing root estimate lock, checks current actor/session/subscription/CSRF before replay and after waits, and compares exact current source/plan/decision pins. The server derives the result from the immutable inserted receipt before commit; calculation failure rolls the whole adoption back. Reusing a key with the same body returns the original receipt without making it current again; a changed body conflicts. Runtime has only narrow protected entry points and no direct new-ledger/helper privileges. Two-second write lock and ten-second statement limits remain.

The ordinary isolated demo uses the same calculator/projector/form, with token-owned state, expiry, mutation bounds and independent mutation receipts. Its new receipt operation is `estimate_adopt`: the originally proposed `estimate_adoption` exceeded the existing VARCHAR(16), so no existing column was widened. No paid endpoint or simulated paid authority is used. Reset continues creating a new synthetic workspace.
