# Mission 26 Part 9A — deterministic baseline reproducibility prerequisite

The unmounted `deterministicBaselineCandidate` reuses Part 4A's existing Retell-only arithmetic mean candidate. It pins one exact calculation configuration, the caller-declared source snapshot, normalized prior-period inputs, and the resulting output with separate digests. Repeating the same configuration and observations, regardless of observation order, yields the same candidate digest. Changing an observed count, coverage receipt or source digest changes that digest. Missing or incomparable history stays unavailable rather than becoming zero.

This is a narrow **reproducibility prerequisite**, not a newly issued baseline forecast or final Part 9A acceptance. It does not duplicate demand arithmetic or create a second forecast engine. The source snapshot digest and coverage receipts remain caller-supplied claims, and no guarded reader authenticates complete Retell lead history. The candidate has no route, saved run, active algorithm registration, calibration, probability, or paid/demo numeric UI. Source authentication, complete reviewed lead identity and coverage, current permissions, a future-facing saved run and independent evaluation remain required before a real baseline can be issued. Part 9B owns calibrated ranges; 9C owns named scenario variations. Mission 26 Part 11 owns immutable run storage and versioning.

Synthetic unit tests prove exact reproducibility, input-change detection, rejection of alternate configurations and invalid records, unavailable propagation, and frozen output. They cannot prove live provider coverage, current tenant authorization, accuracy or production behavior.
