# Mission 26 Part 2A — immutable as-of source snapshots

Status: implementation in progress. No forecast source reader, database snapshot, route or historical backtest is live. The first bounded implementation is the unmounted `src/forecasting/asOfSourceManifest.js` temporal and identity contract with focused tests.

## Temporal rule

An as-of time answers **what NorthStar had recorded by that instant**, not merely when the underlying event happened. A provider can send an older job record tomorrow; that record was not available to yesterday's forecast. A customer can book an appointment for next month today; that future appointment is available to today's forecast. A later correction must not be swapped into an earlier historical snapshot. Source readers must select the exact source revision whose NorthStar `recordedAt` is at or before the cutoff, and must separately retain any business `eventAt`. They must never backdate platform receipt time from a provider-supplied event date.

The manifest currently pins tenant, purpose, target, as-of time, capture time, source kind, source ID, revision, digest, NorthStar record time, optional business event time and active/tombstone state. It rejects future-recorded revisions, duplicate identities, malformed UTC times and arbitrary source fields. Pins are sorted and detached so later caller mutation cannot rewrite an accepted manifest. The 1,000-pin limit is a bounded safety limit, not a claim that 1,000 observations suffice for a target. A larger cohort needs deliberate page/chunk design and a proven aggregate digest, never an unbounded array.

## Remaining Part 2A work

The contract cannot establish that a caller's source digest, revision, recorded time, tenant or consent is truthful. Before this slice is accepted, a trusted, target-specific source reader must derive those fields from the owning canonical tables under current tenant/role/purpose authority. `created_at` alone is not a commit-time history: a transaction can insert a row before the cutoff and commit afterward. A new snapshot can safely capture the rows **visible in its own consistent transaction** at its database-minted cutoff. An old cutoff cannot be reconstructed later from `created_at` alone; require a previously saved snapshot or source-specific proof of historical visibility. Otherwise the historical forecast/backtest is unavailable.

A durable append-only snapshot store must record a canonical digest of the authorized manifest in that same consistent database transaction. It must forbid direct route/client-supplied manifests, update/delete and cross-tenant reads. The stored snapshot must keep only minimized pins or authorized projections; it must not copy raw transcripts, customer contact details, wages or provider payloads. Correction, revocation, retention and current-display invalidation remain Part 2D and Part 11C gates, while immutable historical receipts may remain only where source policy permits.

The first live-source proof can use Mission 24's append-only `canonical_estimate_decisions` as a narrow pipeline source: an owner/administrator, verified through current membership and session, asks a database function to capture the currently visible decision revisions in one serializable transaction. The function fixes the purpose and mints the cutoff itself. It pins decision ID, revision, digest, record time and approve/withdraw state, without copying the approved amount or customer details. A later decision is absent from the frozen result. This is a source-read proof, not a forecast or permission to rewrite Mission 24. Other source kinds need their own owning-authority and purpose review; a generic caller-supplied manifest insert is not acceptable.

Acceptance needs a disposable PostgreSQL run proving as-of source selection, transaction-consistent capture, digest/replay, denied cross-tenant and unauthorized reads, immutability, later correction exclusion, later import exclusion, known future appointment inclusion, and safe unavailability for sources without temporal history. Unit tests of the manifest are necessary but do not satisfy those integration gates. Part 2B owns calendars/windows, Part 2C owns normalized feature values, and Part 3 owns actual backtests/calibration. The Part 1B output contract must not accept a caller-invented snapshot digest as source authority.
