## The comparison that Part 3B must make

A backtest comparison is a separate, append-only evaluation of a **forecast saved before the outcome period** against a later authorized outcome. It preserves the original forecast and the owning actual record. At minimum, each comparison must pin forecast run ID and immutable output digest; prediction as-of and saved-at times; target key/version and canonical dimension scope where required; tenant, service, area, reporting-window and cohort identities; horizon; unit/currency; algorithm version; feature/source snapshot digest; outcome reader/version, outcome cutoff, receipt ID and digest; current permission/retention state; and a reason for any unavailable or excluded pair. A future corrected actual creates a new evaluation revision that supersedes the prior evaluation without editing it.

The released Part 1B output shape has no durable run ID or resource dimension. Part 11B owns the general immutable run store; Parts 4–8 own target-specific forecast and outcome readers. `src/forecasting/rollingBacktest.js` supplies an **unmounted, deterministic comparison contract** over explicitly supplied saved-run and outcome receipts, but it cannot claim a production backtest until those trusted upstream records exist. A synthetic fixture can prove comparison behavior; it cannot prove forecast accuracy or source authorization. Each supplied saved-run receipt must include a validated Part 2B reporting window matching the output horizon, tenant, grain and service/area scope. The result retains its digest, algorithm version and comparable reporting-window basis. Different algorithm versions or noncomparable window contexts cannot be pooled. A difference in period length or operating minutes receives `window_normalization_required` with no paired numeric outcome until a reviewed normalization exists in later authority. Part 3A blocks scoped targets under output v1 until a versioned scope-carrying interface is independently reviewed. This first comparator also blocks cohort-transition targets because output v1 cannot carry their frozen cohort digest. Its allowlist contains only unscoped v1 target identities and is not an active source registry.

## Rolling-origin rules

1. Each origin is the forecast's exact saved prediction cutoff, not a date reconstructed from the later actual. The saved forecast and its source receipt must have existed before the target horizon starts. The Part 3A v1 target gate requires `horizon.startsAt >= forecast.asOf`; a saved-at time after horizon start is ineligible even if an earlier `asOf` string was supplied.
2. Compare successive eligible origins in chronological order. Multiple forecasts for the same horizon are separate runs and must not be silently replaced by the most accurate later revision. A candidate algorithm can be evaluated only against origins for which that exact version was saved or was reproducibly generated from the then-visible pinned source evidence; later outcomes or policy versions may not enter its features.
3. A target outcome must be observed through at least the horizon end, finalized by its owning reader, and captured after the horizon. Event occurrence and ingestion time are different. Late provider records, corrected decisions, withdrawals, disputed relationships and deleted source evidence can make an earlier evaluation superseded or unavailable; they do not rewrite the forecast.
4. Join on exact tenant, target definition, dimension scope, horizon, service/area, cohort where applicable, unit/currency and owning-source identities. A coincident dollar value, customer name or calendar date is never a join key. Missing an authorized outcome is unavailable, not zero; a zero requires a complete observed zero certified by the source reader.
5. Keep excluded, missing, stale, conflicting and not-yet-finalized cases visible in a bounded evaluation manifest. Do not compute error or interval coverage only on easy observed successes without disclosing the denominator and selection rules. Part 3C owns numerical metrics and sample sufficiency; Part 3B produces eligible paired evidence and explicit non-pairs.
6. Evaluation uses a frozen target/algorithm version and comparable-window rule. Changed business calendar, service-area definition, currency, source scope, target version or source policy either has an explicit reviewed normalization or makes that pair ineligible. No cross-tenant or demo-to-paid pooling.

## Minimum contract acceptance

The pure comparator rejects sparse/oversized arrays, duplicate run or outcome identities, forged extra fields, cross-tenant or mismatched target/horizon/unit joins, forecast save after horizon start, outcome cutoff before horizon end, and a supplied latest source record later than its source snapshot or prediction cutoff. It checks that a saved output digest matches the normalized Part 1B envelope. It deterministically orders rolling origins, preserves an observed zero, marks unavailable outcomes without numeric substitution, and produces a detached result. The same historical inputs yield the same comparison digest. It emits paired evidence, **not** an error metric, calibrated confidence, probability, pricing change or scheduling action. Its input receipts and digests are not self-authenticating; only future guarded owning-source and saved-run readers can supply them as trusted evidence.

`tests/unit/m26-rolling-backtest.test.js` checks two rolling origins, deterministic ordering and digest, observed zero, unavailable outcomes, late save/nowcast rejection, cross-tenant/target/window/unit mismatch, premature outcome cutoff, source-time leakage, duplicates, sparse/oversized arrays including a sparse array disguised with an extra key, mixed-algorithm/window refusal, input detachment and scope/cohort target refusal. The later integrated acceptance must use authorized saved runs and source-owned actuals, including a correction after a first evaluation, revoked/deleted outcome source, late-arriving actual, same-horizon competing algorithms, partial source coverage, current tenant permission loss and fictional-demo isolation. PostgreSQL immutability, concurrency, replay and performance gates belong with the later saved-run/evaluation store. Until those records and readers exist, Part 3B's production backtest and empirical accuracy status remain **unavailable**.
