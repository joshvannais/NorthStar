# Mission 26 Part 7A — bounded labor-cost forecast

The historical unmounted `src/forecasting/laborCostPositionDiagnostic.js` remains the arithmetic prerequisite for Part 7A. It reuses Mission 24's `laborPlanContract.calculate` for worker-hours, burden, per-task cents rounding and unknown-rate handling, but it does not authenticate its caller-supplied evidence or issue a forecast.

The Part 7A implementation candidate adds a tenant-private PostgreSQL projection in migration 240, a read-only paid route at `GET /api/v1/forecast/labor-cost/current`, and one compact row inside the existing Command Center Cost & operational risk details. It projects the next 30 days only. Each included job must be current approved backlog and must point to a current, approved and reviewed Mission 24 labor plan pinned to that exact scheduled work. The plan must carry exact owner-saved labor rate, burden, currency and source-applicability evidence. Work that crosses the horizon, lacks exact period attribution or has incomplete source coverage fails closed instead of being partly allocated or treated as zero.

The projection also requires current declared role-capacity commitments for every planned labor role and verifies that the planned minutes fit those exact commitments. This is evidence about declared capacity, not payroll, attendance, worker qualifications or guaranteed execution. A complete covered horizon with no planned work may return zero; missing or incomplete evidence returns unavailable.

Mission 25 learned labor outcomes remain tenant-private and advisory. If an active learned multiplier could apply to a planned service, this implementation returns unavailable unless an accepted compatibility contract proves that applying it would be current, applicable and would not double-adjust a Mission 24 plan. The current contracts do not provide that proof, so the implementation never silently applies the multiplier.

The paid response never supplies a probability, confidence interval, automatic action or whole-business cost claim. It does not cover payroll or attendance systems, off-platform work, material, equipment, travel, overhead, collections or profit. The isolated demo uses fixed fictional data and never calls the paid route. Loading, unavailable and recovery states stay in the same embedded row without creating another dashboard.

Tests cover strict response validation, tenant and role isolation, transaction boundaries, exact plan/rate/capacity arithmetic, learned-evidence fail-close behavior, fresh migration application, paid/demo isolation, responsive rendering, focus, overflow and unavailable recovery in Chromium and Playwright WebKit. The implementation candidate still requires an independent whole exact-head audit and the normal single release before Part 7A can be accepted.
