## Historical receipt versus current use

Part 2A's immutable as-of receipt preserves what the system could see when it was captured. A later correction or withdrawal must **not** rewrite that receipt. It can, however, make a value derived from it unsuitable as a *current* value. Migration `137_canonical_forecast_lineage_current_source.sql` adds one guarded, read-only entry for the existing Mission 24 approved-estimate decision source. It accepts a saved receipt ID, reuses Part 2A's current owner/admin, session, membership, onboarding, subscription and tenant checks, then returns the saved manifest and a fresh bounded current manifest. It requires a serializable transaction so the current source view is consistent and its cutoff is minted after MVCC visibility is fixed. The migration runner places 137 in its existing bounded startup lock and statement-timeout lane. The function copies only decision pins; it does not expose prices, customer details or raw source rows. Its maximum remains 1,000 pins and 262 KB, with no unbounded fallback or direct table grant.

`src/forecasting/lineageCurrentness.js` validates the registered feature and the two manifest shapes, tenant, purpose, target, source kind, source receipt digest, as-of order and historical feature cutoff. It compares the exact source descriptors, **not** the two receipt digests: a newer as-of time alone does not make unchanged sources stale. A new decision, corrected approval, withdrawal tombstone or removed source changes the source set and masks the saved numeric amount. The result says `current`, `stale`, or `unavailable` with a bounded reason. It does not recompute or approve a replacement amount. A later reader must capture a new authorized receipt and calculate a new feature under its definition.

Revoked source permission, expired retention and deletion yield an unavailable projection with no saved amount. This pure contract accepts those states only from a **trusted owning-source and permission reader**; caller-supplied flags are not authorization. Mission 24's first decision source has current account authority and immutable withdrawal revisions, but it does not have an independent forecast-purpose consent, deletion or retention policy to invoke. The PostgreSQL entry proves current account gating and decision corrections/withdrawals; it does not claim that other Mission 25 imports or external sources have been wired. Their own source-specific readers must supply true revocation, retention and deletion status before registration. A source no longer legally retainable cannot be preserved merely because a historical forecast references its digest. Part 11C will own saved forecast-run display invalidation when runs exist.

The Part 2D acceptance boundary is the **only currently registered feature source**. For that Mission 24 source, current owner/tenant/entitlement revocation denies the guarded read, new or corrected decisions and withdrawal tombstones mask old numeric projections, and the historical receipt remains immutable. No M24 decision-source retention expiry or legal deletion event exists to test; the generic v1 unavailable branch and the explicit v2 unavailable capability flags are fail-closed contracts, not evidence of an implemented M25 import lifecycle. Adding a registered feature source stays blocked until its owning reader proves the same lifecycle behavior. Saved-run invalidation, durable worker checkpoints and unattended workers cannot be accepted here because no saved forecast run exists; Parts 11C and 12C retain those gates. This narrows the present evidence claim without changing the frozen mission sequence or treating later controls as complete.

## Replay and restart

The unmounted batch projection processes at most 100 supplied features in pages of at most 25. It rejects sparse or extra-key arrays and validates the whole bounded input before returning a page. Its cursor pins the normalized current manifest **content** and input digest, not merely a caller-supplied receipt digest. A retry with the same frozen inputs returns the same page; a changed source or changed input refuses the old cursor and requires a restart from a fresh authorized source read. This is **pull-based recomputation**, not a background event queue. There is no durable run/cursor store yet, because Mission 26 has no persisted forecast or feature result. A future worker must keep cursor authority server-side and add persistent checkpoint/recovery evidence before claiming unattended multi-run propagation. Revocation and retention must be rechecked on each page; no cursor overrides them.

Disposable PostgreSQL tests cover a saved zero stock becoming stale after a new approval, a later correction and withdrawal, unchanged current source, read-only serializable requirement, member and tenant denial, account entitlement loss, and historical receipt preservation across a new connection. Unit tests cover source-change masking, revocation/retention/deletion masking, source and tenant mismatch, deterministic bounded paging, restart and changed-source cursor refusal. They do not prove paid-production source behavior, external-provider revocation, actual deletion policy, a running forecast, scheduled recovery or a physical device.
