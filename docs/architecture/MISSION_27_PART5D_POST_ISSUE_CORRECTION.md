# Mission 27 Part 5D — post-issue correction and void boundary

Part 5D owns post-issue correction through explicit credit, debit, replacement and void records. Every correction must carry a reason and complete lineage to one exact immutable issued version. A correction appends a new record; it never edits, deletes or reinterprets the issued version.

No issued invoice exists at this release boundary. Released Part 5A cannot create a final approval because the frozen recent-authentication/MFA assurance and due-term and delivery policies are unavailable. Released Part 5B therefore cannot assign an invoice number, create an immutable issue receipt, invoice or receivable. Released Part 5C preserves that absence across all seven lifecycle axes. Part 5D must not fabricate the missing issue in order to demonstrate a correction.

The mounted private owner/administrator read revalidates the exact current Part 5C source chain and returns `m27-invoice-post-issue-correction-v1`. It names all four record classes in frozen order: credit, debit, replacement and void. Each record class is value-free with `issued_invoice_unavailable`, a null value and bounded prerequisite names. No customer, work, amount, currency, document number, due date, invoice digest, receipt or correction value is returned.

Every future record class is bound to the same exact lineage field contract: organization, correction record ID/digest/sequence/type, original issue receipt ID/digest, original issued-version digest, previous correction record ID, source-authority digest, requesting actor, authorization receipts and policy version, reason, and recorded time. These are required field names, not accepted values or new storage authority. Credit/debit additionally require an exact correction amount and bound; replacement requires exact replacement-document lineage; void requires the accepted void lifecycle and remaining-balance evidence. Missing evidence never becomes zero or an empty lineage link.

Credit, debit and replacement require the released `customer_financial.invoice.correct` capability and its `conditional_dual_control` policy. That policy requires an exact current issued document and current Mission 24 authority for a commercial change; it rejects missing amount, bound, authority, identity or currentness evidence. Void separately requires `customer_financial.invoice.void`, exact current issued invoice and remaining balance, an accepted void lifecycle, two different current humans and a reason. Its control mode remains `dual_control`, and single control remains forbidden. This slice does not widen either released policy, mint a grant or claim that any prerequisite exists.

The response records the invariant that the issued version is immutable and that mutation of it is unauthorized. All four append-only record authorizations remain false. There is no POST route because no current issued version exists against which an authorized correction could be recorded. The read creates no credit, debit, replacement, void, numbering event, issue receipt, invoice, receivable, delivery, payment, refund, settlement or accounting effect. Provider-call and receiver-mutation counts remain zero.

Any malformed reference, non-exact upstream boundary, role or tenant mismatch fails closed. Source correction or reopening is revalidated through that same chain and remains value-free.
