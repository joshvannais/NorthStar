## Definition and registration

`src/forecasting/featureContract.js` defines an exact, versioned feature shape. It pins a key and definition version; source kind(s), purpose and target; a named derivation; stock versus observed-window meaning; exact unit key, monetary currency where applicable, allowed decimal scale and sign. Definitions are detached and frozen. A changed derivation, unit, currency or meaning needs a new definition version. A three-letter currency field is a syntax boundary, not proof that a source uses that currency or permission to convert it.

`src/forecasting/featureDefinitions.js` registers one deliberately narrow source-controlled identity: `pipeline.approved_estimate_stock` v1. It means the **count of active latest estimate decisions visible in an authorized as-of Mission 24 decision snapshot**, not the number of new approvals in a reporting period, projected bookings, revenue or issued customer quotes. Its source kind and purpose match the bounded Part 2A capture. The target-complete v2 projection calls only Part 2A's purpose-fixed database entry points, validates the exact tenant receipt and currentness result, and then applies `active_decision_count`; it never accepts a caller manifest, digest, count or state. The v2 registered normalizer requires a known amount to equal its authenticated bounded source-record count. Unknown definition versions fail closed.

## Feature value states

The value contract distinguishes `known`, `missing`, `stale`, `conflicting` and `inapplicable`. A known numeric value is a bounded decimal **string** with the definition's unit, currency, precision and sign; zero is permitted only as an explicit value, never as a fallback for missing evidence. A trusted empty source snapshot establishes a known count of zero without a latest source row. The registered approved-estimate stock requires a latest decision timestamp for a positive count. All other states carry no usable amount and require a coded reason. V1 remains unchanged. Additive value contract v2 pins an exact bounded source-record count to every authenticated receipt, permits a stale null source timestamp only when that count is zero, and keeps conflicting values dependent on a latest source time. Inapplicable has no source pin. Generic missing values may retain a paired authenticated snapshot digest and source-record count when an authorized read proved absence; the scoped approved-estimate coverage-refusal projection emits neither and makes no authenticated-completeness claim. A caller-supplied state is only structurally valid, not proof of freshness, conflict resolution, applicability or source authority. Those decisions belong to target-specific readers and policies.

Every value has tenant and definition identity plus an exact digest of that definition, an as-of instant with microsecond-safe ordering, the exact unit, and optional source receipt pin. The definition digest prevents a later code change under the same version from silently matching an old value. Known, stale and conflicting values require a source snapshot digest. A known value still must be computed from the authorized receipt; the contract does not authenticate a caller-supplied source digest. `observed_window` features require a validated Part 2B window for the same tenant whose end precedes the as-of time. `as_of_stock` features have no reporting window. Future known scheduled events need a separate reviewed temporal definition and must not be mislabeled as historical actuals. Window validation is structural; a future reader must authorize the underlying Business Profile and honor overnight opening-date attribution.
