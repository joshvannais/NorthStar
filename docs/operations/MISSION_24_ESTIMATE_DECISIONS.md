# Human estimate decisions: bounded Phase 1 adoption

This package adds an explicit current owner/admin decision to the existing shared customer drawer. A person records the reviewed work scope and exact before-tax price for quote preparation, revises that decision, or withdraws approval. The recorded estimate and Polaris calculation remain unchanged. This is an incremental Phase 1 authority adoption, not completion of Phase 1 or of Pricing/Presentation phases.

## Authority and consumers

The [architecture](../architecture/MISSION_24_ESTIMATE_ARCHITECTURE.md), [consumer inventory](../architecture/MISSION_24_ESTIMATE_CONSUMERS.md) and nine-phase [roadmap](../roadmap/MISSION_24_ESTIMATING.md) remain additive. Private Polaris and future Capella Risk Lens use the same recorded estimate identity and provenance. Authorized internal risk analysis can contain private costs; a future customer quote needs its own explicit safe projection. This implementation does not send, export, charge, calculate taxes, alter machine price, create a new estimator, or implement Risk Lens.

Mounted paid consumers are the existing customer drawer in Dashboard, Leads and Communications. Its selected canonical estimate is read through the existing owner/admin review GET; the same transaction reads current membership/session/operator authority, recorded calculation and new decision history. The new POST at `/api/v1/canonical/estimates/:estimateId/decisions` uses current tenant/session/CSRF and owner/admin authority. The ledger is not added to broad canonical projections, worker/member views, or public customer routes. Existing machine-price labels and routes remain calculated recommendations and cannot attest human approval.

Demo uses the same drawer, form validation and server decision projector. Its read and mutation adapter is token-scoped and synthetic, calls only `/api/demo/command-center/estimates/:estimateId/*`, and stores practice history inside the existing demo session. Paid ledger identities never become demo authority. Existing same-origin intent, workspace revision, admission, expiry, reset and mutation caps remain. Twenty decisions per demo estimate are allowed within the existing 24-action session cap. Reset explicitly clears the fictional workspace and its practice history. Original simulate/reset receipt digests retain their prior shape.

## Immutable contract

Migration 057 adds `canonical_estimate_decisions`, protected by statement-level UPDATE/DELETE/TRUNCATE rejection. Runtime direct table access and helper execution are revoked; only the narrow read/mutate functions are granted. All migration DDL, ledger registration and runtime grants/verification commit in the existing single migration transaction. No old migration is rewritten. The existing demo mutation check additionally allows `estimate_review` within its unchanged VARCHAR(16) column.

Each receipt retains tenant, selected estimate, revision, previous decision, actor/membership/session, actor display name, source pins, approval/withdrawal, scope, exact price string, currency, reason, fixed explicit confirmation version, request digest and creation time. The API projects only the display/history fields and necessary concurrency pins; no idempotency secrets or demo receipt internals are returned. Read history is newest-first, capped at 20 with total/truncation stated; history remains stored. A decision revision is monotonic and bounded at 10,000 per estimate.

Source pins match the released estimate review contract: estimate, graph, customer, operation, opportunity, snapshot/digest, calculation version, normalized input fingerprint, Business Profile identity/version/hash and supporting fact IDs. Snapshot date remains displayed and checked against the selected estimate in the drawer; its immutable snapshot identity binds it, rather than introducing an independent writable date. Missing costs remain missing and zero remains zero. The human price is independently entered, never silently seeded from machine advice. Price is a nonnegative exact two-decimal string, up to 12 integer digits; null, blank, exponent, excess precision and negatives fail. Currency must match the recorded estimate. No conversion or tax arithmetic occurs.

Mutation uses SERIALIZABLE and finite statement/lock timeouts. Subscription eligibility and existing actor helper locks protect current membership/account/profile/session/onboarding authority; the estimate row serializes decisions. Current role/session/CSRF is checked before replay and again after lock waits. Expected decision revision/digest and exact source pins must match for a new event. Identical actor-scoped idempotency replay returns the original receipt without reactivating a superseded approval; changed details with the same key conflict. A concurrent decision or committed authority change yields a safe conflict/denial with no partial event. Unknown outcomes can be retried with the same immutable body/key. UI conflicts preserve text but require refresh/reconfirmation. Switching customers discards a stale response/draft.

## Recovery and rollout gate

Migration 057 is a new release risk. No Part11 waiver applies. Normal startup must complete all migration checksum and separate-role grant checks before serving. Deployment to any real environment, production backups and production recovery remain separately governed; this package only rehearses disposable local data.

The source-controlled recovery artifact is [estimate-decisions-read-only.patch](../../recovery/estimate-decisions-read-only.patch). Apply it to the exact candidate source in an isolated recovery build. It changes only `src/estimating/decisionPolicy.js` from enabled to disabled. Both paid and demo decision POSTs reject even replays, while current authorized GETs and shared UI preserve saved approval/withdrawal and history. UI states that new decisions are paused; it never claims saved approval is absent. The ledger, migration and projector remain present. Existing unrelated features retain their authority. This is an application decision-mutation pause, not a database disaster restore or a guarantee about old still-running processes.

Before using recovery operationally, quiesce/drain every normal writer instance and verify the exact recovery build is serving all decision traffic. Do not roll back to the pre-ledger e9124d application: its review says approval is not recorded and cannot truthfully interpret saved decisions. Never drop ledger/history to make old code start. Fix forward from the candidate/recovery-compatible source, preserving 057 and all decisions; re-enable mutation only after independent exact-build checks and the governing release decision. A newly discovered schema defect needs its own additive migration and reviewed recovery impact, not editing 057 after application.

`tests/api/m24-decision-upgrade-recovery.js` mounts the actual released base in a separate checkout, populates estimates, upgrades through candidate startup, creates paid/demo decisions, restarts the source-patched recovery build against the same disposable database, checks truthful reads and blocked writes, then restarts the normal build and appends the next revision. It compares all 54 previous checksums (numbered through 056) and complete estimate/decision records. This is a populated upgrade and application forward-recovery rehearsal; physical backup restoration and private production evidence remain unavailable.
