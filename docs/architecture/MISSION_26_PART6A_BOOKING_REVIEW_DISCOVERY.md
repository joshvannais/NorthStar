# Mission 26 Part 6A: recent booking review candidates

The paid owner/admin `GET /api/v1/forecast/booking-reviews/candidates` route examines only the 100 most recent tenant human scheduling approval source orders, then filters them for a current appointment with an accepted issued estimate and a still-current reviewed price. It returns appointment and approval IDs, scheduled time and before-tax price so a booking review screen can show a specific job. It does not mark that job booked or create a forecast. A later accepted scope, changed schedule or price can make a displayed candidate stale; the human review write checks the source again and may refuse it. The UI must refresh rather than assume a displayed candidate grants write authority.

The indexed raw source-order window is materialized before joining or filtering while the tenant commercial lock is held, so old unmatched approvals cannot cause an unbounded search. Opportunity-oriented estimate and accepted-delivery indexes keep each guarded lineage lookup local to the candidate opportunity instead of walking the tenant's full commercial history inside the 100-row loop. Appointments already carrying a commercial review are excluded. The response says `recentWindowOnly: true` and identifies its 100-approval window limit. Older potential candidates require a later paginated discovery design; an empty list means no **observed review candidates in this recent window**, not zero work in the business. The runtime role cannot read source tables directly; only paid owner/admin sessions can call the guarded route.

The focused mounted fictional-tenant test exercises one positive candidate, fail-closed suppression above the 1,000-approval per-appointment write bound, suppression after a later same-opportunity acceptance, absence after review, other-tenant empty result and member denial. A paid/demo frontend journey, rendered wording, cross-source contention, source-complete period, release and full Part 6A acceptance remain open.
