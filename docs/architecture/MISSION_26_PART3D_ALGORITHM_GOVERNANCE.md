## Versioned registry boundary

A **production registration** must identify its target key and definition version; algorithm key and immutable version; deterministic or statistical method; reviewed implementation/build digest and parameters; accepted feature definitions; output contract version; supported reporting grains; training/calibration receipt and policy where applicable; and exact tenant/context applicability, unit/currency and interval-policy identity. Changing the calculation, target meaning, input policy, training data, attribution, unit or interval policy requires a new version, never a silent edit. The code implementation digest is a **claim** until a trusted build/registration workflow proves it. A registered definition is not an activated forecast or a source grant.

`src/forecasting/algorithmCatalog.js` provides a bounded pure **tenant-identified static candidate identity** catalog. It validates shape, distinct key/version identities, target and output-version pins, method kind, feature digests and supported grains, then returns a detached sorted digest. It intentionally does **not** represent exact service/area or dimension context, unit/currency, interval policy, evaluation-policy applicability or an active pointer. The catalog cannot register, compare, execute or activate a contextual algorithm; a versioned context/units/policy interface must be independently reviewed before those operations. Its tenant ID is a caller-supplied identity, **not authorization**; a future guarded reader must verify ownership of every feature/training receipt against the server-derived tenant. Deterministic algorithms may not claim training evidence. Statistical candidates require a training-receipt digest but remain untrusted until that evidence and tenant isolation are verified. A globally reusable implementation never implies cross-tenant pooling of private observations or calibration.

## Human-reviewed promotion and recoverable rollback

Migration 218's selection is an append-only tenant-scoped internal-experiment event, separate from definitions, evaluation receipts and saved forecast runs. A mutation requires current owner/administrator forecast permission, server-derived tenant, CSRF, idempotency key, exact expected revision, a fresh current reviewed-comparison digest, reason, actor and timestamp. It rechecks review currentness at decision time and cannot reuse a review for a second event. A promote or rollback event affects only possible **future internal-experiment** execution: old outputs, run digests, approved estimates, schedules, invoices and historical evaluation records remain unchanged. All production, real-forecast and paid-serving eligibility flags remain false.

Rollback is a new reviewed event to the still-compatible deterministic carry-forward version, not deletion or alteration of an earlier promotion. It uses the same access and expected-revision guards, a fresh review, a reason and the exact promotion event being reversed. If the evidence or permission changed, rollback is unavailable until an authorized owner creates and reviews current evidence. Recovery from a failed deployment never silently repoints a tenant. The durable production run pointer remains a later governance concern; migration 218 records internal-experiment review decisions only. No algorithm may self-promote, and neither Polaris advice nor an LLM can sign the human decision.
