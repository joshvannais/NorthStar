# Mission 26 Part 11B — forecast run receipt and immutable ledger

The Part 11B implementation candidate mounts the existing `forecastRunReceipt` identity contract behind a tenant-private owner/admin issue, read, history, comparison and controlled-rerun boundary. Additive migration 255 stores an immutable run receipt, its ordered output manifest and any separate supersession lineage event. Each receipt pins the server-resolved tenant and prediction cutoff; the exact current Part 11A settings revision/digest; the trusted Part 2 source snapshot, reporting-window and feature-set digests; the promoted Part 3 algorithm definition, installed implementation and build digests; calculation and output-contract versions; and the ordered target/version/output manifest. Run ID and creation time remain outside the deterministic input and result identities. Complete authenticated zero remains a stored value; unavailable evidence returns no receipt or value.

Issuance currently supports the released `demand.inbound_leads` version `v1` deterministic point target for the next authenticated business-local month. It resolves tenant and actor from the paid session, locks and revalidates the exact current settings revision, checks its explicit monthly target/horizon selection, captures the released authenticated Part 4A origin once, validates the current Part 9A algorithm and pre-outcome chronology, and atomically stores the canonical output and receipt. Reviewed settings may describe more monthly periods, but the released Part 4A evidence authority supports only the next local month; later months remain value-free unavailable rather than being extrapolated. The runtime role can execute guarded entry functions but cannot read, update, delete or truncate the receipt, output or supersession tables.

Idempotency binds the tenant, actor, key and exact request. A retry returns the same stored receipt without executing the calculation again; replay of an older key reports its historical latest/superseded position instead of presenting it as current. Conflicting keys, stale settings, invalid horizons, clock reversal, unavailable source evidence and bounded lock contention fail closed. A supersession verifies the referenced same-tenant run ID and digest under current source, settings and algorithm authority, refuses an already superseded run, appends a new lineage event and preserves the older run.

The comparator accepts two distinct stored runs only. `reproduced` means identical pinned input and result identities, `result_mismatch` means identical pinned inputs with different stored output manifests, and `input_changed` means any pinned input differs even when the result digest matches. A run cannot reproduce itself. Digest equality establishes receipt identity only; it does not turn source attestations into provider-independent coverage, natural calibration or a promise of future results.

Controlled rerun loads the preserved authorized origin evidence and the exact still-installed algorithm implementation, executes the bounded arithmetic from those retained inputs, and compares a fresh output manifest with the stored result. It never rebuilds an old run from current inputs. Missing retained inputs, changed settings/source/algorithm authority, permission loss or an unavailable exact executable version returns a named value-free unavailable state. Source corrections and revocations therefore hide retained values while the immutable receipt rows remain governed historical records; Part 11C still owns the broader correction, deletion, outcome and advice lifecycle.

The shared Settings surface contains one compact paid/demo run-receipt experience. Paid workspaces never fall back to demo evidence. The demo uses isolated fictional receipts and makes no paid settings or run calls. Loading, errors, permission loss, stale settings/source/algorithm evidence, reset, expiry and recovery clear receipt values, digests and comparisons before rendering another state. The UI labels point forecasts separately from calibrated ranges and named scenarios, performs no forecast arithmetic, and authorizes no action.

The candidate has focused contract/repository coverage, fresh full-migration PostgreSQL coverage through migration 255, bounded-lock and idempotency conflict probes, immutable privilege checks, fresh-connection reads, source revocation and settings-staleness gates, and Chrome plus Playwright WebKit desktop/mobile light/dark paid/demo journeys. Final Part 11B acceptance remains open until one independent exact-head audit accepts the frozen candidate, one normal PR is merged, the sole automatic deployment applies migration 255, and health/root/demo checks pass. CI, physical Safari/devices, live provider/private-production evidence, natural tenant history, backup-restore disaster evidence and founder visual approval remain unavailable.
